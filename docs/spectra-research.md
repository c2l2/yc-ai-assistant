# 在研究專案使用 Spectra

「先討論」時，在聊天裡比較研究問題、可行做法和還缺的證據。若使用者只請你寫大綱，就交付大綱。當使用者說「照這個方向做」，你有權自行判斷是否開 change，直接執行已授權的範圍。

| 工作情境 | 做法 |
| --- | --- |
| 修正錯字、回答一個問題、改一段已選定的文字 | 直接完成，回覆實際修改或答案。 |
| 做一個需要跨對話接手的分析，同時更新模型、程式與圖表，或提出日後須核對的研究主張 | 在相關工作區找已有的 change。結果與範圍相同就接續；新問題才另開。 |
| 執行中改了研究問題、識別假設或主要結論 | 說明這項選擇的影響。方向已獲授權時更新原 change；需要作者決定時，列出選項及各自的證據。 |

## 找到這次工作的規格

先看專案根目錄的 `AGENTS.md` 和本次要改的成果。從成果所在目錄往專案根目錄查找 `.spectra.yaml` 和當地說明，依本案設定找到規格、變更及 CLI。已設定的工作區可能在論文子目錄，也可能使用較早的 `openspec/` 路徑。

研究專案裡的 `yc-ai-assistant/` 是共用工具。副本所附的 `yc-ai-assistant/docs/spectra/` 記錄助手自身的行為；研究規格放在研究成果所屬工作區。只有改共用助手本身時，才從助手的來源 checkout 開啟該套規格。

第一次需要追蹤工作時，若專案尚無 Spectra，選能涵蓋這次成果的根目錄，依本案可用的 Spectra 版本就地初始化。例如使用 `spxa` 的 Codex 專案可在該目錄查看 `spxa init --help` 後使用 `spxa init . --tools codex`。保留原有專案指令，按實際生成的位置記下入口。若生成的指引預設要使用者點名提案，把已授權工作可由 AI 自行開 change 的約定寫進該專案的有效入口，並核對提案 skill 的觸發說明。缺少工具時，先找專案 wrapper 或本機可用的 CLI；若安裝受限，回報所缺工具並繼續已授權、可獨立驗證的部分。

## 從提案到交付

1. 找到要交付的成果及其來源。讀當地規格、相關 change 和現稿或程式。工作區提供 CLI 時，可用其 `list` 與 `status` 檢查進度。已有變更若經驗證後刻意保留，可從驗證紀錄讀到原因。
2. 用當地的 Spectra 提案流程寫下這次要回答的問題、修改範圍及判準。適用的假設、證明義務或重現條件寫進變更規格。具體執行步驟放在這個 change 的 `tasks.md`。若有團隊週報，分工留在定稿週報，連回 change 即可。
3. 在既定範圍內執行、重跑檢查並核對實際成果。專案若約定先展示擬加入的 LaTeX，照該約定辦理。遇到已確認的範圍調整，在同一項工作更新規格與步驟。
4. 驗證時寫清楚這次支持的主張、證據位置和仍待檢查的條件。依本案約定歸檔；回報時分清楚哪些已執行、哪些有驗證證據、哪些已歸檔。下次問進度時，對照生效規格、相關變更及目前成果回答。

**理論例。** 要把固定階數下的結果推廣到隨樣本數成長的階數，先寫出要控制的餘項及允許的階數範圍。交付時連到推導與核算，指出哪一步仍依賴額外條件。數值特例能檢查等式，對一般命題仍須給出推導。

**實證例。** 要把已核定的新樣本定義套進主表，列明納入條件、估計對象與輸出表格。驗證時連到產生表格的程式、輸入版本和結果，說明有沒有從原始資料重跑。若只用保存的估計值重算平均數，就如實記錄這次驗證的範圍。
